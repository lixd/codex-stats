# 小而美：性能与界面精修评审

评审日期：2026-10-15。源码基线 v0.2.9/build 11，提交 d60eeeb。状态：**第一批已获批准并实现为v0.2.10；其余建议尚未实施**。以下“已核验的现状”记录评审时的v0.2.9，不是新版当前状态。关联 R14/R17；现有重建契约仍以 [设计基线](design.md) 为准。

## 产品方向

保留菜单快速查看、分析窗口深入查询的两层结构。精修的目标是启动轻、后台安静、信息易读、交互可预测。优先完成现有功能的质量，不增加 Provider、费用服务、账号、云同步或复杂主题系统。不以删掉统计证据、隐藏告警或猜测缺失数据换取表面整洁。

## 已核验的现状

- Core/App/Report 为 Swift，原生 SwiftUI/Charts/AppKit，零第三方运行时依赖；后台 actor 串行扫描、64 KiB 读取、局部自动释放池已经存在，不是待增加能力。
- 文件级缓存按路径/大小/mtime复用；增长文件仍全文重解析。即使所有文件命中，scan 仍运行全局归组、历史核验和计量处理。见 [扫描器](../Sources/Core/CodexLogScanner.swift)。
- 已批准 B 仍是原型，正式 MenuPanelView 仍为 288pt 原布局。B 原型约288×469pt，不能把它说成更矮的布局。见 [B设计](ui-design-b.md)。
- Requests 的360pt固定详情和218pt导航，叠加48pt内容边距，在950pt窗口下留给列表约323pt；已保留原生横滚，但同时可见的信息有限。旧合成预览 inspector-950-light.png也呈现列表仅剩少数列。静态图不证明真实滚动或点击。
- SessionsContent 的 matching 反复过滤/排序，selectedSession 在行构建时又访问 matching；Token排序比较器内重复聚合会话用量。Requests 与菜单同样在视图求值中计算聚合/排序。这里是可定位的潜在开销，尚无本轮 Time Profiler 量化结论。
- MetricTile 主副两行重复同一缩写；共用卡片的缺失副标题硬编码“日志缺少部分缓存字段”；当前仅缓存卡传入缺失状态，所以不能声称已出现推理字段误提示，未来复用需改为字段对应文案。TokenDetails中英混用，界面含大量9–10pt辅助文字，刷新/退出等小控件未统一命中区约定。
- 设计已明确两处身份缺口：文件名生成的归组ID与真实Session ID未完全区分；缺少元数据时所有权比较可能误用归组ID。准确性问题应先于视觉扩展修复，不能直接把现状当作已满足真实身份目标。

## 建议顺序

| 顺序 | 工作 | 原因与验收 |
|---|---|---|
| 0 | 修复真实身份边界 | 添加缺失session_meta、thread_id等于文件名的合成反例；真实ID缺失显示未记录，无法证明所有权的用量不接受；CLI/UI一致 |
| 1 | 先减少重复聚合，再调扫描策略 | 将当前范围汇总与列表查询结果按报告修订、范围、当地日期、时区和查询条件复用；行内只读取选中ID/已算值，不重新过滤排序全部会话；精确计量快照不变 |
| 2 | 接入已选B菜单 | 保持288pt；落实总量与四指标层级、动态范围标签、未知字段、刷新状态、先关闭菜单后打开分析及退出；不能只把原型数字替换就交付 |
| 3 | 分析窗口精修 | 收紧头部与品牌占位、统一字体间距与文案；详情采用宽度自适应的右侧呈现；保留查询、选择及表格数据可达性 |
| 4 | 完成实机质量验收 | 长时间运行、刷新稳定性、睡眠唤醒、深浅色、高对比/减少动态效果、键盘/VoiceOver与目标系统验证 |

## 性能方案取舍

第一步复用派生结果，不缓存正文，不将所有历史记录复制成多套缓存。当前报告变化、范围变化、本地跨日、时区变化时必须正确失效；后台刷新不能导致用户选择和滚动位置无故重置。无变化扫描可在明确文件集合/根路径/时间桶一致的前提下复用报告数据，但保留正确的成功时间与诊断语义。

字节级追加和磁盘持久缓存列为后续候选：只有在固定样本证明增长文件重读或重启扫描成为主要瓶颈时再做。追加解析必须覆盖文件截断、同路径重写、部分末行、计数器重置、历史引用和全局去重；持久缓存必须有版本失效与隐私边界。不能先引入数据库，再寻找它解决的问题。

保留用户选择的默认30秒刷新，避免重叠扫描；评估timer tolerance以合并后台唤醒，但不能擅自把设置改为长间隔。没有变化的刷新应尽量不触发昂贵表格重建。

## 视觉与交互方向

- 菜单：落实B的总量主视觉，色彩只表达输入/输出/缓存/推理语义；保持原生背景与系统控件。刷新、退出具有明确hover/focus及足够点击区；不要用额外大图标或长说明挤占菜单。
- 总览：主值有唯一视觉焦点；副标题提供口径/数据完整性而非重复主值；详细原始值保留悬停与复制。缺失说明按对应字段生成。中文标签统一，协议字段留在原始详情。
- 窗口：导航和顶部工具栏降低重复占位；具体尺寸先在UI目标设计里定稿。950/1120pt分别验收，不能依赖放大窗口掩盖布局问题。
- 请求详情：宽窗口保留右侧并排；窄窗口优先评估侧边覆盖面板或折叠导航，使关键时间/模型/总量可读；不让固定详情宽度把列表压到只剩两三列。关闭后保留搜索、排序、选中项和位置。
- 告警：保留现有分级和折叠，不隐藏真正影响统计的情况；默认一行摘要，展开按原因、影响范围、是否能修复组织，普通继承信息不表现为故障。
- 精修：空态区分无日志/无匹配/读取失败；未知速度说明缺失证据，不填0；复制成功给轻量反馈；增加清晰的键盘焦点、搜索快捷入口及关闭详情ESC；先验证现有ESC行为，避免重复实现。

## 性能证据与建议门槛

本轮进程检查没有发现运行中的CodexStats，**没有新的实际App内存测量**。已有 [验证历史](../VERIFICATION.md) 的约350MB/39文件固定输入：扫描cold3.185s、warm75.18ms、追加123.17ms；v0.2.7 App在35秒的当前footprint28.0MiB、峰值35.5MiB。这些是历史受控输入，不能解释为当前真实日志、完整页面或长期运行的占用。

建议沿用现有固定输入目标：cold≤5s、warm≤100ms、范围筛选≤50ms；另加大记录集的搜索/选行测试，目标交互响应≤100ms。App菜单首次绘制与首扫完成分开计时，不能用骨架渲染代替可用数据时间。建议为同一350MB输入建立完整App常驻footprint≤100MiB、峰值≤200MiB的初始预算，完成真实基线后定稿；它们是建议而非已达成承诺。长运行应在预热后反复刷新/开关详情观察是否稳定，区分字体/Charts一次性缓存与持续增长。

## 验证与交付边界

性能变更前后使用相同冻结输入，对比精确Token、记录身份、模型、日期桶与诊断；分别记录RSS/footprint/峰值及宿主。UI状态覆盖正常、首扫、旧数据刷新、失败、无匹配、未知字段、长模型名；实际点击菜单→分析需确认弹窗收起。不能用静态预览替代鼠标/键盘/长期驻留验证。

第一批建议范围：身份边界修复、派生结果复用、B菜单接入及字段文案；分析窗口视觉改版先出同内容明暗/窄宽方案，确认后再实现。后续任务先更新requirements及相关UI/data设计，完成测试后才能更新实现基线。评审后用户批准第一批，实现与验证状态如下。

## 第一批实施结果（2026-10-15）
