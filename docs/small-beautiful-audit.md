# Codex Stats「小而美」审查

审查日期：2026-10-15。基线：`11f2a937971c40b29a2b4d69ff6bb79c5eaec91f`，v0.2.10 / build 12。范围：当前源码、契约、合成数据测试、原生静态布局及受控资源测量。**这是审查与建议，不是实施批准。** 没有修改产品代码、现有测试或脚本，没有安装、退出或替换用户 App，没有提交或推送。

结论：产品方向和技术栈已经足够克制，下一步最有价值的是修正两处计量边界、消除两条可测的重复计算路径，以及让统计异常在各页可见。没有证据支持重写 UI、引入数据库、持久缓存或新增功能。

## 2. 实际数据流与生命周期

1. `CodexLogScanner.scan` 枚举 sessions/archived_sessions，按路径、大小、mtime 复用解析元数据；变化文件全部重读。64 KiB 是读取块大小，不是最大 JSON 行长度。正文解析后释放，不进入报告。
2. 真实 Session 身份归组 → 合法 owner 的压缩证据和 response 冲突核验 → legacy 主流选择 / 继承前缀 → 原生与累计通知配对 → 去重/差分 → 接受记录及日、小时、模型聚合 → Turn 与请求估算关联。
3. `ScanWorker` actor 串行扫描；`UsageStore` 在主 actor 发布报告。扫描中再次刷新只合并为一次后续扫描。Timer 更改时销毁旧 Timer，回调弱引用 Store，没有发现无限堆积 Task 的证据。
4. 菜单、总览与模型页共享一个当前范围摘要；请求、会话页仍在视图求值路径同步筛选/投影。CLI 使用同一个 Core，固定输出全部范围。**各页合计一致只能证明聚合一致，不能证明上游接受的记录没有多算。**
5. 菜单先关闭自身 hosting window，再打开分析；最后窗口关闭不退出；显式退出调用 AppKit；同 bundle ID 的新实例让位于已有实例。独立 AppKit harness 能验证这些机制，不能替代生产 MenuBarExtra 的真实点击。

定位：[Scanner](../Sources/Core/CodexLogScanner.swift) 68–237、578–702、768–917 行；[Store](../Sources/App/UsageStore.swift) 20–38、85–155 行；[场景](../Sources/App/CodexStatsApp.swift) 5–30 行；[生命周期](../Sources/App/AppLifecycle.swift) 4–63 行。

### A01：通知配对和重发去重没有共享状态

**问题和影响。** 同一 Turn 中，一个原生响应 R 为输入 100、输出 10，随后收到最近一次用量通知 U。`R → U → U` 或 `R → U → R → U` 在本轮均得到 **220 Token / 2 行 / 零告警**，合成真值为 **110 Token / 1 次响应**。会话、模型、菜单和 CLI 会一致地显示多算结果。关联 T03/T04/T07。

**证据。** [Scanner](../Sources/Core/CodexLogScanner.swift) 684–702 行按 response 只做一次邻接配对；871 行对已覆盖 last-only 通知直接跳过，没有把该用量登记进重发签名集合；880–885 行把后续相同通知当成签名第一次出现而计入。累计通知已覆盖分支 817–823 也需纳入修复范围。

复现见 [accounting-repro.py](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/research/accounting-repro.py) 和 [当前输出](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/accounting-crosscheck.json)。独立直接编译的 Core CLI 与本轮 SwiftPM CLI 对全部 7 个用例输出一致。单组 R/U、累计真实增长、不同 response 的相同用量、foreign owner 重发等对照符合预期。

**最小修复与取舍。** 为已配对通知登记相同的保守重发证据，后续相同 last-only 在没有独立新响应或可信累计增长时不再计入，并按现有规则提示歧义。不能一律按 Token 数值去重，否则会删除真实的等大小请求；不能让拒绝 owner 的用量经通知重新进入统计。无身份同值新请求仍可能保守少计，这是已有口径，应保留诊断。

**验证。** 新增通知在前/后、通知单独重发、native+通知一起重发、累计 companion 后转 last-only、换 Turn、不同 response 等值、累计增长、活动/归档及错误 owner 的真值断言，再检查所有聚合一致。没有读取真实日志，不能据此断言用户现有总量多算多少。

### A02：完整 Turn 的附加关联存在平方级重复工作

**问题和影响。** [Scanner](../Sources/Core/CodexLogScanner.swift) 578–628 行在每个完成 Turn 内重新过滤整个 rows、展开 copies.frames、计算 pairedNotifications、检查全部 frames，最后再遍历全部记录回填。缓存只省解析，省不掉这一步。长会话会拖慢首次可用数据和每次后台刷新。

**本轮复现。** 单文件、每 Turn 一个有真实身份的原生响应，所有 Token 与 Turn duration/TTFT/输出覆盖断言通过。`-O` 构建，warm 每档 3 次：

| 完整 Turn 数 | 文件大小 | cold | warm 中位数 |
|---:|---:|---:|---:|
| 250 | 144,123 B | 0.133 s | 0.085 s |
| 500 | 288,123 B | 0.547 s | 0.323 s |
| 1,000 | 576,123 B | 1.883 s | 1.321 s |
| 2,000 | 1,152,123 B | 5.144 s | **4.368 s** |

规模增 8 倍、warm 约增 51 倍，与代码中的重复全量遍历吻合。标准 350 MB fixture 没有完整 Turn 生命周期，不能覆盖此瓶颈。原始结果见 [规模证据](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/scale-results.jsonl)，生成器和 harness 见 [性能研究](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/research/performance.md)。这是扫描耗时，不是 UI 卡住 4 秒的实测。

额外对照保留相同 2,000 条原生响应和开始事件，仅移除 `task_complete`，warm 中位数为 **9.63 ms**，完整 Turn 场景约为其 454 倍。两者都命中解析缓存，Token/身份一致；对照只要求性能元数据为空。这进一步支持关联阶段是瓶颈，见 [对照结果](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/control-results.jsonl)。

**最小修复与取舍。** 每次扫描先按会话组织 logs，每个物理文件只计算一次通知配对，建立 Turn→记录索引与原生帧索引，减少全量展开和回填。无 Turn、foreign owner、未配对 counter、损坏/历史引用仍须保留对覆盖完整性的否决能力，不能仅按 turn_id 分组就跳过时间区间核验。短生命周期索引增加少量内存，换取少做重复工作；不引入持久缓存。

交叉复核特别要求保留 597 行 `inherited: 0` 的完整配对，不能误用 aggregate 裁剪继承前缀后的结果；601–603 行相关性包含 frameRange、同 Turn、区间内时间或缺时间，不能简化为只看 Turn ID。先修计量，再以修正后的完整报告为性能等价基线。

**验证。** 全部 Turn/请求估算/计量回归，以及 250–2,000 Turn 冷暖规模对比；逐字段比较记录、原始用量、模型、桶和可选性能。期望增长接近线性，另记录峰值内存。墙钟性能放在受控基准，避免不稳定的单元测试时间阈值。

### A03：累计缓存/推理差额被“修正”成错误精确值

**问题和影响。** 两帧 `(input, output, cached, reasoning)` 从 `(100,100,0,0)` 到 `(110,110,50,50)`，每帧自身合法，但子集差额 50 大于父项差额 10。本轮第二条记录变为 `(10,10,10,10)`，两个 known 均为 true，零告警；总缓存/推理成为 10。输入/输出合计仍正确，缓存、非缓存输入和推理却提供了没有证据的精确值。关联 T01/T06/T08。

**证据。** [Models](../Sources/Core/Models.swift) 41–51 行只验证单调性，随后通过 16/18 行构造器 `min` 夹紧子集；[Scanner](../Sources/Core/CodexLogScanner.swift) 837–844 行当作成功差分，860 行的原生抵扣也调用同一方法。[合成反例输出](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/accounting-crosscheck.json) 的 `impossible_subset_delta` 可复现。

**最小修复与取舍。** 差分必须验证子集增量不超过父项增量，禁止夹紧后仍标 known。先在数据设计中明确两种选择：保留可证明的父项增量、将异常子项标未知并诊断；或返回不可差分、仅用合法 last 并重建基线。后者代码更少，但可能保守少计父项，不能在未明确口径时默认采用。诊断应为“累计计数器无法核对”，不能把单调增加的反例误称“回退”。

**验证。** 缓存/推理分别越界、有无 last、known 转换、原生抵扣；原始快照可查、告警可见、父项与未知字段政策一致。不为好看的缓存命中率补值。

### A04：会话列表仍把日期格式器创建放在逐会话循环中

**问题和影响。** [SessionsContent](../Sources/App/SessionsContent.swift) 24–45 行每次 body 计算匹配列表；26/27 行分别调用每会话 `usage` 和 `modelUsage`。两者各自创建非“全部”范围边界，最终走 [Models](../Sources/Core/Models.swift) 174–185、213–226 行的新 DateFormatter。N 个会话至少重复 2N 次。`recentSessions` 已排序，视图还会再排序。

**本轮证据。** 主 actor 上构造每会话一条真实 Core 元数据记录，执行与生产默认匹配路径相同的 API 调用和排序，各 5 次；这是同步投影基准，**不是实际 SwiftUI 帧率/点击测量**。

| 会话数 | 今天列表投影中位数 | 全部列表投影中位数 | 今天 UsageSummary 全量重算中位数 |
|---:|---:|---:|---:|
| 1,000 | 329 ms | 1.50 ms | 1.32 ms |
| 5,000 | **2,161 ms** | 6.44 ms | 5.53 ms |

各层总量、模型和小时断言通过。差异说明下一步应处理会话日期边界，不应继续扩张已经有效的摘要缓存。用户在大量会话时搜索、选中、切范围可能触发这段同步工作。最小样本不代表用户实际有 5,000 个当日活跃会话。

**最小修复与取舍。** 一次查询捕获一次 now/bounds，批量生成会话行所需用量与模型，最终只排序一次。可增加一个窄的 Core 查询入口，不需要引入新状态管理框架；先去重复工作，再判断是否需要单个有界投影缓存。

**验证。** today/7/30/all、跨日/DST、无用量但范围内活跃会话、搜索/排序/选择；相同样本重复测量并独立验收实际窗口响应。当前设计总纲“主线程只发布结果”的表述需在实施时纠正为真实职责边界。

### A05：数据质量和刷新错误只在部分页面可见

**问题和影响。** 当前合成报告含 3 条警告/错误和 1 条信息：菜单与请求页显示提醒，模型页、会话页没有相同统计状态入口，侧栏仍显示绿色“本地数据已连接”。刷新整个根目录失败后，这两页仍只有侧栏泛化的“读取失败”，缺少错误原因；用户在当前页无法判断是损坏、字段缺失还是旧成功数据。关联 R11/T08。

**证据。** [DashboardView](../Sources/App/DashboardView.swift) 94–106 行仅看 `errorMessage`，不看报告诊断；116–154 行共享 header 不展示异常；ModelsContent 及 [SessionsContent](../Sources/App/SessionsContent.swift) 44–82 行没有 StatusBanner/DiagnosticSummary。与 [UI 状态矩阵](ui-design.md) “旧数据+错误 Banner”的全窗口表述存在差距。当前模型 950/1120 原生预览可观察到绿色侧栏；静态布局不能证明用户点击后的导航。

本轮还对脚本自身创建的合成目录临时改名，触发同一 Store 的刷新失败，确认旧成功报告仍在、错误非空，然后恢复目录。实际原生预览：[有诊断的模型页](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/models-950-light.png)、[成功后刷新失败的模型页](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/audit-failed-refresh-models-light.png)、[会话页](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/audit-sessions-950-light.png)。这验证状态和呈现缺口，没有修改真实日志。

**最小修复与取舍。** 分析窗口统一提供一处紧凑扫描状态：成功/保留旧结果/不完整报告，风险数量可进入已有诊断详情；信息级 history 不升级成故障。避免每页重复一套大 Banner。菜单诊断按钮目前按明确设计只打开分析，这是当前行为，**不是单独的新 bug**；可一并设计为打开并定位诊断，解决入口与目的地不一致。

**验证。** 从模型/会话页触发首次失败、成功后失败、部分文件错误、信息级历史、恢复成功；成功时间保持、旧数值不消失、原因可达。对真正未知和“未完整记录”保持原有诚实表达。

### A06：本地安装更新没有受控失败边界

**风险和影响。** [install-local.sh](../Scripts/install-local.sh) 7–12 行先删除现有 App，再复制并 `open`；没有运行实例检查、暂存校验或回滚。若复制失败/中断，旧可用副本已被删除；若用户忘记退出，已有实例策略可能继续保留旧进程，安装脚本的成功文字不能证明运行的是新版。[build-macos.sh](../Scripts/build-macos.sh) 18–31 行也在编译成功前清空目标产物。

**证据等级。** 删除→复制→启动顺序经静态确认；README 已提醒先退出旧版，这是现有缓解。**本轮没有对安装目录做故障注入，没有复现用户更新失败**，因此列为待验证风险，不宣称发生过数据丢失或 App 损坏。本轮临时路径原生构建、严格签名核验成功，证明正常构建路径可用。

**最小修复与取舍。** 安装前若同 bundle 已运行则明确失败并提示手动退出，不自动结束用户进程；在同卷临时位置完成复制和校验后再替换，失败保留原副本，成功后核对启动的路径/版本。构建也先完成临时产物再替换目标。仅改交付脚本，无需引入自动更新服务。

**验证。** 对隔离目标目录和独立 bundle 测试复制失败、编译失败、中断恢复、重复实例与成功更新；断言失败后旧产物散列不变、成功后运行身份匹配。不要用 stub 的成功输出证明真实安装成功。

### A07：窄窗口应优先保障“身份 + 总量”可同时读到

**问题和收益。** 当前 950 pt 窗口打开请求详情后：218 pt 导航 + 48 pt 内容边距 + 360 pt 详情，使列表约剩 323 pt，只看到时间/项目/部分模型，总量和其他数字依赖横滚。模型页同宽度下总计列也在右侧可见区之外。横滚已实现，这不是数据丢失或表格失效；但快速核对一条记录为何高耗量需要额外往返。此为旧延期项的本轮复核，不重复拆成“导航太宽、详情太宽、表格列太多”三条建议。

**证据。** [DashboardView](../Sources/App/DashboardView.swift) 59、112 行；[RequestsContent](../Sources/App/RequestsContent.swift) 76–124 行；[当前 950pt 请求预览](../.trellis/tasks/archive/2026-10/10-15-small-beautiful-audit/evidence/inspector-950-light.png)。B 菜单的总量层级、长名称、未知字段和深浅色本轮预览良好，不建议为装饰再改。

**最小方案与取舍。** 先评估将总量移到身份列附近，保留所有字段可达、选择/搜索/排序/滚动上下文。调整列优先级比整体重做视觉系统更小。折叠导航或覆盖式详情属于延期备选，后者改变当前 R09 的并排详情契约，不能混入小修。具体选择仍须原生方案和用户确认，不能把本文当作新布局批准。

**验证。** 950/1120 pt、最低高度、长项目/模型、未知和十亿数值、明暗；再实际验证横滚、Esc/关闭详情、焦点与选择保留。不要仅通过把最小窗口调大来掩盖问题。

## 6. 推荐下一批与暂缓项

建议下一批按以下五项确定范围；每项实施前更新 requirements 及对应 data/UI/design 文档，再进入代码：

1. **计量可信度小修：A01 + A03。** 先定异常累计子集政策，再补反例；影响核心准确性，预计合计 1–2 日。
2. **完整 Turn 关联去重复：A02。** 已有秒级实证；优先局部索引，保留全部覆盖否决语义。
3. **会话查询共用日期边界：A04。** 不改视觉、不加功能，可直接降低主线程同步成本。
4. **全窗口统计状态与诊断入口：A05。** 避免“数字可见但风险不可见”；同时做生产菜单、搜索、选择、Esc、复制和键盘的真实操作验收。
5. **安全的本地替换流程：A06。** 先在隔离目录复现失败，再做小脚本级修复；不加入后台自动更新。

暂时不值得做：数据库、磁盘持久缓存、字节级追加、监听所有日志、为了节能擅改30秒默认值、通用状态框架、整体 UI 重写、主题/装饰系统、费用/额度/账户/云同步。当前标准扫描和 App 采样没有证明它们的必要性。A07 的窄窗口改版有收益，但已是延期方向，宜在准确性、卡顿和告警可达性后单独出小方案；复制反馈、字号与间距也应由实际操作/无障碍问题驱动。
